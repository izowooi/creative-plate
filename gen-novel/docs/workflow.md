# 소설 빌드 파이프라인

## 시작의 순서

설정을 전부 완성한 뒤 쓰려 하면 매일 쓸 사건이 사라지기 쉽습니다. 반대로 아무 기록 없이
계속 생성하면 관계·능력·시간이 흔들립니다. 먼저 인물 2명과 첫 무대를 잡고, 집필에 필요한 설정만 확장합니다.
작가 답변을 정리할 때 `확정`, `제안`, `미정`을 구분하고, 사용자 발언을 출처로 남깁니다.
처음 준비된 ENTJ/INTJ·ENFP 카드는 선택지를 담았으며 실제 인물의 성격 완성본이 아닙니다.

첫 주는 ① 인터뷰·최소 설정 ② 3~5화의 짧은 arc 기획 ③ 첫 화 시험 집필
④ 작가 문체 피드백 반영 ⑤ 다음 화 연결 ⑥ 한 arc의 작은 결말 ⑦ 취향 회고 순으로 시도합니다.
하루를 건너뛰어도 실패가 아닙니다. 가장 최근 확정 회차가 재개 지점입니다.

## AI가 수행하는 하루의 작업

1. `AGENTS.md`, 작품 index, 상태를 확인한다. 사용자 요청의 민감 부분을 제거하고 `local/journal/`에 먼저 기록한다.
2. 요청에서 인물·장소·물건·옛 약속을 추출한다. `search`로 lore와 과거 요약을 찾고 실제 원문을 확인한다.
3. 원 요청을 `local/briefs/<unique-id>.md`에 저장하고 `start`로 context를 준비한다. 이전 확정본과 관련 lore가 들어갔는지 확인한다.
4. AI가 context를 읽고 `plan.md`와 실제 `draft.md`를 작성한다. CLI가 글을 써 준 것으로 보고하지 않는다.
5. 다른 관점의 편집 패스를 수행한다. 한 AI가 순차적으로 기획자·작가·편집자 역할을 바꾸면 충분하다.
6. 요약·전체 다음 상태·필요한 lore 대체 카드를 작성한다. 원고를 수정하면 세 자료도 다시 검토한다.
7. 작가에게 원고 경로, 핵심 수정 사항, 변경되는 정사, 미해결 질문을 보여 준다. 작업 결과를 journal에 남긴다.
8. 작가가 명시적으로 확정했을 때만 `approve`한다. 그 뒤 `check`와 `status`로 확정 회차를 확인한다.

시작 전에 핵심 구상이 미정이면 질문을 모은다. 기획에 대한 질문이나 대답도 journal에 저장한다.
외부 앱의 대화, 사용자가 보내지 않은 프롬프트, 접근할 수 없는 과거 대화를 자동 수집하지는 못한다.
이 프로젝트 대화에서는 AI의 기록 규칙으로 보관하며, 별도 프로세스가 모든 키 입력을 감시하는 구조가 아니다.
CLI `log --request-file ... --response-file ...`는 이미 민감정보를 제거한 두 파일을 고유한 UTC 이름으로 묶는다.
자체적으로 모든 종류의 비밀을 탐지하지 않으므로 저장 전에 반드시 제거한다.

## 수정과 확정

수정 요청마다 새 run ID를 쓴다. 수정 지시와 기존 원고 경로를 brief에 넣고 `start` 후
기존 초안을 참고하여 새 draft를 만든다. 이전 run을 덮어쓰지 않는다.
확정된 원고를 잘못 썼다면 원본을 직접 고치지 않고 다음 회차의 정정 설명과 상태/lore 변경안으로 반영한다.
과거 전체를 다시 쓰는 retcon은 별도 작업이며, 영향받는 모든 이후 요약·상태를 점검하는 계획을 먼저 만든다.

`review.md`의 첫 줄은 `verdict: PASS` 또는 `verdict: REVISE`다.
PASS는 작가 승인과 다르다. CLI는 비어 있는 자료, 검토 미통과, 준비 이후 정사 변경,
원 요청/context 변경을 차단하지만 문학적 완성도나 진실한 승인 여부를 자동 판정하지 못한다.
AI는 승인 문구를 스스로 만들어 확정하지 않는다.

확정은 임시 디렉터리에 원고·검토·요약·상태·lore 변경·승인·해시를 모두 쓴 다음
완성된 회차 디렉터리를 한 번에 게시한다. 실패 시 부분 확정본이 나타나지 않는다.
동시에 두 작가가 같은 프로젝트를 수정하지 않는다. 경쟁 확정은 같은 회차 디렉터리를 덮어쓰지 못하지만
초기 lore 편집과 확정을 병렬 실행하는 작업까지 동기화하는 서버는 아니다.

## 기억의 계층과 검색

| 층 | 무엇을 보관하나 | 언제 읽나 |
|---|---|---|
| 핵심 | 작품 약속·문체·주요 인물 | 매번 |
| 현재 상태 | 시간/위치·능력/부상·소지품·지식·관계·미해결 약속 | 매번, 직전 확정 snapshot |
| lore | 장소·조연·조직·물건·마법 규칙 | ID 지정, 키워드 일치, requires 연결 |
| 회차 기억 | 사건·선택·변화·출처 | 직전 + 검색 후 지정한 과거 회차 |
| 원문 보관 | 전체 원고와 과거 대화 | 사실을 재확인할 때 해당 파일만 |

각 lore는 안정적인 ID 하나를 갖는다. 이름이 바뀌어도 ID를 바꾸지 않는다.
아래의 story 카드는 실행 시 `local/story/`를 뜻한다. `story/`는 배포 템플릿이며
`init`으로 local에 복사한다. 작가 답변을 반영한 실제 카드와 index는 local에서 편집한다.
`index.json`의 `keywords`에 별칭을 넣고 `requires`로 필수 연관 항목을 연결한다.
새 lore는 story에 `제안` 상태 카드와 index 항목을 만들고 새 run에서 사용한다.
기존 lore의 변경은 run의 `updates/<id>.md`에 **카드 전체**를 제안한다.
확정 후의 실제 정사는 최초 카드 위에 회차별 updates를 번호순으로 적용한 결과다.
따라서 최초 story 카드만 읽어 현재 정사라고 생각하지 않는다. `Novel.canon()`이 적용 결과를 반환하며
`start`의 context에는 그 결과가 들어간다. 이미 확정된 카드의 story 원본을 직접 수정하지 않는다.

현재 상태는 무한히 늘어나는 일지가 아니다. 이미 해결된 약속은 해당 회차 요약으로 옮기고
열려 있는 것만 ID·첫 등장/최근 변경 회차·관련 인물·해결 조건과 함께 유지한다.
장기 비밀은 `독자 공개 여부`, `알고 있는 인물`, `공개 조건`을 적어 시점 누출을 막는다.
arc가 끝나면 작은 결말과 관계 변화를 요약하고 닫힌 항목을 현재 상태에서 내린다.
끝없는 연재는 작은 arc의 결말을 반복하고, 완결형은 장기 질문의 답과 마지막 선택을 향해 정렬한다.

기본 packet 예산은 60,000 UTF-8 bytes이며 문서 검색 비용과 모델 입력 크기는 별개다.
과거 전체를 context에 넣지 않으므로 작품이 100만 토큰을 넘어도 매일 작은 자료 묶음으로 집필한다.
필수 자료가 예산을 넘으면 `start`가 실패한다. 현재 모델의 실제 여유를 확인해 예산을 조정하여 새 run을 만든다.
확정 전 state 제안에서 해결된 항목을 회차 요약으로 옮겨 작가 승인 후 압축을 반영한다.
이미 확정된 state나 기존 lore 원본을 직접 편집해 우회하지 않는다. 필요한 내용을 조용히 자르지 않는다.
키워드 검색은 의미 검색이 아니므로 별칭·관계 ID를 관리하고, 미해결 복선은 상태에서 빠뜨리지 않는다.
`rg -n '물건명|옛 이름' local/final local/journal`로 요약 밖의 원문도 찾을 수 있다.

## 퇴고 체크

- 연속성: 시간·이동 거리·이름·마법 비용·소지품·부상·누가 무엇을 아는지 일치하는가?
- 인물: MBTI 설명 없이 선택으로 성격이 보이는가? 조연도 자기 목적이 있는가?
- 재미: 작은 목표, 방해, 선택, 결과가 있는가? 일상 회차도 관계나 이해가 변하는가?
- 가독성: 설정 설명이 행동을 끊는가? 시점이 새는가? 대사만 읽어도 인물이 구별되는가?
- 여운: 앞의 구체적 행동/물건이 뒤에서 의미를 얻는가? 마지막에 감정을 다시 해설하지 않는가?
- 기억: 요약과 다음 상태가 수정된 최종 원고를 반영하는가? 미정 사항을 정사로 바꾸지 않았는가?

문학적 평가는 자동 테스트로 증명할 수 없다. 작가의 “다음 편을 읽고 싶은가”와
“이 문장이 내 취향인가”가 최종 기준이다. 첫 세 회차 뒤 좋아한 대사·싫어한 문장 유형을 style 카드에 반영한다.

## 백업과 복구

코드는 Git으로 백업되지만 local/ 원고와 대화는 push되지 않는다.
사용자가 관리하는 백업 도구로 `story/`와 `local/` 전체를 함께 보관한다. 실제 설정은 `local/story/`에 있다.
현재 컴퓨터 밖의 백업은 아직 설정하지 않았다. 외부 업로드 위치는 사용자가 선택한다.
복원할 때 빈 임시 폴더에 코드·story·local을 함께 복사한 후
`python3 novel.py --root <복원폴더> check`로 확정 파일의 무결성을 검사한다.
해시는 우발적 변경 탐지용이며 악의적인 manifest 변조나 백업 장치의 안전성을 보증하지 않는다.
